# 金工小子工程训练设计报告

金工小子面向工程训练中心的参观、教学、讲解和空间导引场景。最终形态不是单一网页或单一地图，而是一套安装在青龙机器人顶部横屏上的嵌入式交互终端，并由多模态后端、真实三维地图、微信小程序入口和实体组件共同支撑。

## 汇报口径

项目最终可按四条工作线说明：

| 工作线 | 说明口径 | 主要成果 |
| --- | --- | --- |
| 总体方案、嵌入式交互终端与跨端集成 | 面向机器人顶部横屏，完成需求拆解、应用状态、触控交互、真实三维导航和微信小程序统一入口 | Android / H5 主线、小程序分包、3D 地图、路线拓扑、发布门禁 |
| 实体组件与软硬件协同 | 围绕终端安装、结构适配、现场展示和机器人本体装配展开 | 机器人载体、安装结构、三维打印、装配调试、演示流程 |
| 多模态自然交互 | 让机器人能持续感知、理解用户意图并给出自然反馈 | 唤醒、聆听、语义理解、问答、TTS 播报、打断与状态反馈 |
| 智能后端与任务控制 | 将模型理解结果转为问答、导航、状态切换和设备控制等可执行任务 | DuplexKit 后端、工具声明、导航事实、状态同步、安全中断 |

这四条线不是彼此割裂的模块。移动端应用承担嵌入式交互终端，小程序承担跨端集成入口，后端承担多模态智能与任务编排，实体组件保证这些能力能落到真实机器人上。

## 1. 需求端

### 1.1 场景需求

工程训练中心的使用对象包括参观访客、上课学生、任课教师、设备管理人员和机器人维护人员。用户并不是坐在电脑前慢慢操作，而是在现场面对机器人，可能边走边问、边看边确认、边听边触摸屏幕。因此系统需要同时满足四类需求：

| 需求 | 具体含义 | 验收方式 |
| --- | --- | --- |
| 状态展示 | 机器人空闲、聆听、理解、回答时要一眼可懂 | 待机页、聆听页、对话页和专家页横屏截图完整 |
| 自然交互 | 用户可以通过语音提出问答或导航需求，触控用于确认、补充和纠错 | 后端指令能驱动 `wake / listening / processing / chat / expert / map` 状态 |
| 空间导引 | 地图必须能解释房间、门、走廊、楼梯、二层半平台和路线节点 | 路线按门口、走廊、楼梯口、平台、目标点逐段展示 |
| 跨端调用 | 微信端可以快速打开同一套地图和导航能力，不能只是截图或临时 H5 | 小程序包内 WebGL、同房间 ID、同路线规则、同发布门禁 |

真实约束包括：

- 顶部屏幕以横屏展示为主，第一眼必须像机器人终端，而不是桌面管理后台。
- 声控不是唯一入口，用户必须能通过触摸继续、回退、切换视角或修改路线。
- 地图不能穿墙，不能从公共楼梯直接进入 104 / 106 / 108 的独立二层。
- 202-5 属于二层半平台，视觉上要和二层区分，同时下方仍有承托结构。
- 小程序发布版不能依赖 `localhost`、`5173`、公网临时 H5、截图贴图或静态 PNG 地图。
- 后端不能凭房间名猜测距离、时间和下一节点，必须使用应用端回传的导航事实。

## 2. 设计方案

### 2.1 总体系统

技术主线采用 Tauri 2、React、TypeScript、Vite 和 Three.js。Android / H5 是嵌入式终端主线，小程序使用微信 WebGL canvas 与 Three 适配层，后端通过 DuplexKit 提供多模态实时链路和工具调用。

```mermaid
flowchart LR
  User[现场用户] --> Voice[语音与触控输入]
  Voice --> Backend[多模态智能后端 DuplexKit]
  Backend --> Tools[任务工具: 问答 / 专家 / 导航 / 状态]
  Tools --> Directive[结构化指令与导航事实]
  Directive --> Terminal[嵌入式交互终端]
  Terminal --> Standby[待机与聆听]
  Terminal --> Response[对话与专家回答]
  Terminal --> Map[三维空间导航]
  Map --> Topology[房间 / 门洞 / 走廊 / 楼梯拓扑]
  Map --> Scene[Three.js 真实模型场景]
  Scene --> Android[机器人 Android 横屏端]
  Scene --> Mini[微信小程序 WebGL 端]
```

核心文件和职责：

| 模块 | 文件 | 职责 |
| --- | --- | --- |
| 应用状态 | `src/shared/appTypes.ts`、`src/App.tsx` | 定义 `standby / chat / expert / map` 和后端指令入口 |
| 后端桥接 | `src/backend-bridge/directives.ts`、`src/duplexkit/useDuplexKitRealtime.ts` | 将后端工具请求、音频状态和导航事实接入前端 |
| 地图主体验 | `src/features/map3d/Map3DApp.tsx` | 3D 场景、模型、图层、相机、路线、标签、面板 |
| 地图语义 | `src/features/map/data/mapData.ts` | 房间、空间、门洞、楼梯、中心线、控制点 |
| 路线服务 | `src/features/map/routeService.ts`、`runtime.ts` | 路线计算、逐段导引、导航进退、标签策略 |
| 小程序宿主 | `miniprogram/` | 首页、响应页、地图分包、WebGL canvas、后端 bridge |
| 后端依赖 | `vendor/DuplexKit` | Realtime 服务、工具规划、房间目录、导航进度事实 |

### 2.2 嵌入式交互终端

应用只有四个主状态：待机、常态对话、专家问答和地图。聆听与理解属于待机页内的过程状态，避免屏幕上出现复杂输入框。这样更像机器人“脸”和“提示屏”，而不是一套桌面软件。

<p align="center">
  <img src="assets/evidence/process/final-terminal-state-strip.png" alt="嵌入式交互终端最终状态拼图" width="920">
  <br>
  <sub>最终终端状态：待机、聆听、常态对话和专家问答均围绕横屏机器人使用场景收敛。</sub>
</p>

设计细节：

- 待机页只保留机器人表情、右下角地图入口和左侧低干扰抽屉。
- 聆听状态用机器人表情、音量波形和简短提示表达，不要求用户读复杂文字。
- 对话和专家页把回答文字放在视觉中心，小机器人降为右下角辅助状态，避免遮挡。
- 后端调试入口保留但默认隐藏，不抢占产品主界面。
- H5 deep-link 支持 `mode=chat / expert / listening / map`，便于后端和 QA 直接验证状态。

### 2.3 三维空间导航

地图从旧版手工 SVG 迁移为真实模型参照 + 语义拓扑。运行时主模型为 `public/map-models/jingong.glb`，来源于 `models/金工中心模型.3ds`；fallback 为 `jingong-fallback.glb`，来源于 STL。DWG / SKP / 标识 PDF 用于校准空间名称、门洞和楼梯关系。

### 2.4 路线与导引

路线设计围绕真实行走，而不是画一条直线。用户最关心的是“现在在哪、下一步到哪个门/楼梯/转折点、终点在哪里”。因此路线输出被拆成逐段导引：

```mermaid
flowchart LR
  A[房间中心] --> B[房间门口]
  B --> C[走廊中心线]
  C --> D[转折点 / 楼梯口]
  D --> E[楼梯上口 / 平台]
  E --> F[目标门口]
  F --> G[目标中心]
```

关键路线约束：

| 路线 | 必须满足 |
| --- | --- |
| `101 -> 104-2F01` | 经过 104 内部楼梯 |
| `101 -> 106-2F` | 经过 106 内部楼梯 |
| `101 -> 108-2F04` | 经过 108 内部楼梯 |
| `108-lobby -> 202-5` | 经过公共楼梯和 202 二层半平台 |
| `101 -> 208` | 经过公共楼梯和二层公共走廊 |

导航进度允许用户手动点“到达”进入下一段，也允许后端通过语音工具调用 `navigation.next` / `navigation.previous` / `navigation.status`。后端播报时只使用应用端回传的当前段事实，不自行估算距离和时间。

### 2.5 多模态智能后端

后端从“以后再接入”的设想，升级为已锁定的全栈依赖。当前主仓库通过 `docs/backend-duplexkit-version.json` 锁定 DuplexKit：

| 项 | 内容 |
| --- | --- |
| 后端仓库 | `https://github.com/ElysiaFollower/DuplexKit.git` |
| 分支 | `main` |
| 锁定提交 | `167b6a8861666b63c3bdcbf91567ef12fac5e7fd` |
| 提交说明 | `Ground navigation answers in app progress facts` |

后端提供实时语音链路、工具规划、房间目录、导航事实注入和安全边界。公开工具包括：

| 工具 | 作用 |
| --- | --- |
| `map.open` / `map.close` | 打开或关闭地图 |
| `map.set_origin` / `map.set_destination` | 设置起点或终点 |
| `navigation.start` | 启动导航 |
| `navigation.next` / `navigation.previous` | 下一段或上一段 |
| `navigation.status` | 查询当前段、下一节点和剩余距离 |

导航相关回答需要基于 `navigation_progress`，其中包括当前节点、下一门/楼梯/转折点、目标、当前段、剩余距离、预计时间和方向状态。这样可以避免“房间认不全”“距离乱猜”“不知道当前走到哪一段”等问题。

### 2.7 实体组件与软硬件协同

## 3. 验证过程中发现的问题与迭代

### 3.1 交互终端迭代

早期界面更像桌面端：入口多、浮层重、面板连续滚动、右侧操作不够明确。横屏验证后暴露出这些问题：

| 问题 | 影响 | 迭代结果 |
| --- | --- | --- |
| 待机页信息过多 | 机器人“脸”的感觉被破坏 | 改成纯表情 + 地图 FAB + 抽屉 |
| 浮窗不可关闭或露半截 | 触控端不适合连续滚动 | 面板改为 Material 风格，可关闭、可分页 |
| 对话/专家页机器人遮挡文字 | 回答内容不够清楚 | 机器人移到右下角，回答文字居中优先 |
| URL 只能直达地图 | QA 和后端无法直接验证 chat/expert/listening | 增加 `mode=chat/expert/listening` deep-link |

### 3.2 地图几何迭代

地图问题是整个项目迭代最多的部分。早期先做手工平层地图，随后引入真实 3D 模型、门洞、走廊、楼梯和 202 平台。反复验证后，明确了一个原则：地图不能只是“看起来像楼”，而要成为可计算、可解释、可导航的空间结构。

| 问题 | 根因 | 处理 |
| --- | --- | --- |
| 房间和走廊不清 | 只画房间，没有对未命名空间分类 | 增加 corridor、restroom、service、storage、reserved、support |
| 墙体、门点、房间点漂浮 | marker 和墙体高度散落在渲染逻辑里 | 集中 render policy，普通门点隐藏为热区，关键点才显示 pin |
| 楼梯像碎片 | 楼梯视觉和上下 landing 没有统一 | 重建 landing、梯段、踏步、扶手和上下口配对 |
| 二层与二层半混乱 | 202 平台既不是普通二层，也不能悬空 | 增加二层半平台和下方承托结构 |
| 总览、单层、分层不一致 | 不同视图各画各的 | 统一闭合空间模型，视图只是同一结构的不同表达 |

### 3.3 导航与语音协同迭代

路线最初只负责从起点到终点，后来发现现场用户更需要“下一步应该走到哪里”。因此导航从整体路线升级为节点级导引：

- 当前点、下一门/楼梯/转折点、终点 pin 高优先级显示。
- 边标签不再铺满地图，详细说明放到路线面板。
- 用户到达一个节点后可以手动点击“到达”，也可以通过语音说“下一步”。
- 后端只能播报前端回传的当前段事实，避免自行编造剩余距离或时间。
- 模拟器没有方向传感器时，界面明确提示地图按真北显示。

### 3.4 后端接入迭代

后端接入后，设计文档需要从“前端接收指令”升级到“前后端协同闭环”。验证中重点发现并处理了四类问题：

| 问题 | 处理 |
| --- | --- |
| 智能体容易提到无关模型或平台 | 后端提示词强化身份和场景边界，回答围绕金工小子和工程训练中心 |
| 房间号识别不全 | DuplexKit 房间目录与前端 53 个房间做一致性校验 |
| 导航过程缺少当前段认知 | 增加 `navigation_progress`，后端播报当前段、下一节点、剩余距离 |
| 工具声明可能漂移 | `check:fullstack:contracts` 校验工具、远端、锁定提交和脚本 |

### 3.5 小程序迭代

小程序经历了几条被验证后放弃的路线：

| 尝试 | 放弃原因 |
| --- | --- |
| WebView 打开 H5 | 依赖外部服务和域名，不是打开即用 |
| 静态 PNG / 截图贴图 | 看起来像地图，但不能旋转、缩放、选择和真实寻路 |
| 小程序自绘简化地图 | 功能和移动端差异大，容易回退到旧地图 |
| 包内 WebGL + Three 适配 | 当前发布目标，能复用地图语义和路线规则 |

小程序最终门禁不仅检查页面能打开，还检查禁止 WebView、禁止 localhost、禁止全图 PNG 贴图、支持起终点组合、支持后端 bridge、支持 release AppID 和分包配置。

### 4.5 结果评价

最终系统已经从“地图页面”升级为“机器人交互终端 + 三维空间导航 + 多模态智能后端 + 微信跨端入口”的完整闭环：

- 用户看到的是机器人状态和清晰路线，而不是调试按钮或后端参数。
- 地图知道房间、走廊、门、楼梯和二层半平台之间的关系。

- 小程序不是演示截图，而是按发布门禁约束的自包含入口。
- 文档、代码、验证脚本、后端锁定提交和截图证据已经形成可追溯链路。
